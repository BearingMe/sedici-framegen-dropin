# Known issues deferred to after the refactor

Status (2026-11-10, K1-K165): 34 open, 100 fixed or resolved, 12 obsolete (the AMD path, K31, K32, K94 and K21 among them),
1 retracted claim (K30). The original K1-K26 were found while building the vrr presenter, the output
multipliers and the P2.2 coverage on `experiment/cobalt-otter` (through `f95b54d`); K27 onward are in
later tables. K145-K149 were found porting the C++ `diagnostics`, configuration, ffx ABI and the
router/context/session to Rust on `experiment/rust`; K163-K165 were found by the Rust test-parity
slice (`docs/rust/test-parity.md`). The decision was to fix them on the refactored architecture, not to patch the old code.
Each entry names its evidence and the milestone expected to own it. "Measured" means a game capture or
offline check; "code" means read from the source; "suspected" means not yet demonstrated.

Entries are never deleted. A row that turned out not to be a bug, or was replaced by the AMD removal, is
marked Obsolete, Retracted or Hazard. Some open rows are **not product defects** and are kept for the
record: K16 (accepted counter semantics), K23 and K24 (offline test limits), K36 (accepted unattended-run
gap), K101 (log evidence hazard), K112 (load-sensitive checks), and K54 (an intermittent test timeout, possibly
the same cause as K112). Overlaps: K127 repeats part of K98; K57 exercised K29; K55 and K73 are both
fence-wait trust; K39, K40, K41, K47 and K48 are one retention cluster.

Entries marked **[arch]** constrain the target design; the resulting notes are in
[architecture.md](architecture.md#constraints-from-known-defects). The static
pre-refactor review (historical) is in [audit.md](audit.md); the coverage map and tracked
expected failures are in [reliability.md](reliability.md#current-coverage-and-gaps-p22-baseline).

| ID | Problem | Evidence | Owner |
| --- | --- | --- | --- |

| K12 [arch] | In `"vsync"`/`"game"` the game's reference to its native chain is never released, which could block the game creating a new chain on the same window after destroying the wrapper. | Code `route_create` (reference handed over only for vrr); suspected, no failing run | P2.4 **Fixed in P4.3 (82a0843).** Confirmed by the new `sedici_abi_window-replace-vsync` scenario: in `vsync`/`game` (and any vrr fallback) the wrapper kept the caller's handed reference, so after the wrapper was destroyed a new chain on the same window failed with the old one still alive (the test then crashed). `Swapchain::wrap` now takes over the handed references when it keeps presenting through the original chain.
